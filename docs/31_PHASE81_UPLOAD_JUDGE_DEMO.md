## PDF selection, storage and revision workflow

### Generate results after extraction

Extraction stores course candidates; it does not itself enqueue course screening, career assessment or an Action Plan. That missing visible handoff caused the owner's successfully parsed upload to show empty recommendation pages. The new **Generate results** control calls the existing protected APIs in sequence, using `mode=offline` throughout and `research=false` for course screening. It reuses fresh exact-revision jobs/results, validates completed Pydantic/OpenAPI structures and parent fingerprints, and opens the saved recommendations. It never creates mappings, grants academic approval, invokes a live provider, or substitutes sample results. If a completed assessment has no admissible recommendations, it opens that evidence-limited result without submitting an invalid plan.

Progress is bounded to 90 seconds and status polling; changing workspace/hiding/leaving cancels client work, while already queued jobs stay durable. **Check progress** reuses the same idempotency key and saved jobs after an unknown outcome. A queued career/plan may report that its evidence packet is not yet ready; only status is polled until completion, and terminal stale/restricted results remain blocked. New uploads now select the actual imported revision and clear analysis/career/plan IDs from the preceding revision. This also applies to an explicitly historical import without changing which revision is active.

On the owner's real, separately attributed 36-course upload, actual UI submission → worker → PostgreSQL → protected API retrieval produced **36 course findings, one request to obtain reviewed occupation mappings/eligible evidence, and one evidence-review pathway with an Action Plan**. Their job states are **SUCCEEDED / PARTIAL / PARTIAL**; an independent database connection verifies exact lineage, all-course coverage, nonsynthetic flags and no academic approval. Null model names and offline execution are explicit. The brochure has no reviewed detailed syllabus and the current local workspace has no admitted real reference matches sufficient for substantive academic changes. This result establishes working software handoff and honest uncertainty, not real curriculum accuracy or live Claude verification.

The separate document the owner uploaded into the fictional sample remains in that synthetic lane, with its own new revision/results and explicit synthetic labels. Its earlier populated fixture revision is preserved. ## Controlled judge access and revocation

There is no public unauthenticated guest/session service. The supported fallback is an **authenticated controlled read-only preview**. An administrator privately gives the judge only the launcher's `reader` token, scoped to the isolated fictional institution(s), with exactly `read` permission. Never share the complete `auth.private.json`: it also contains operator/admin test grants. Do not use an institution containing real/private records as the judge scope.

Enter the reader token in the normal **Scoped operator credential** field, then choose **Explore Sample Programme**. No PDF or new model generation is needed. The UI hides upload and review controls; the API independently denies upload, live-analysis, review and global-source operations. A foreign institution grant cannot read the sample. Browser credentials remain in tab memory and are cleared on disconnect/reload; they are not bundled, placed in URLs or stored in local/session storage.

The private access policy stores hashes and is read on each request. Removing the reader principal revokes its subsequent access. Ending the owned preview revokes the entire ephemeral environment and removes its schema only after the worker stops. A copied token-only file must also remain private and be removed when no longer needed. Controlled shared tokens have no named judge identity, automatic expiry or SSO; do not present them as production authentication.

During this verification, a prior read-only demonstration token appeared in a diagnostic accessibility snapshot. It was revoked and replaced; direct protected requests independently verified **the old token returns 401 and its replacement returns 200**. That prior preview has since been stopped, and the current preview uses fresh scoped grants. Do not reuse an earlier copied token. No token value is recorded in source, this receipt or a public URL. Keep private login fields out of accessibility/diagnostic captures during future demonstrations.

The synthetic launcher clears provider credentials, explicitly installs mocks and blocks provider HTTP. Its process-only execution gate permits the **mocked synthetic workflow**; the `access-context` flag can therefore be true inside this test scope. This is not a persistent external-processing approval or evidence of a paid request. Read-only authorisation independently prevents judge submissions. Persistent external-processing/research defaults stay disabled, and the launcher does not read or modify them. Actual Phase 8.1 paid usage and billing are not observed; live request count is zero.
