## What was actually diagnosed

The owner's screenshot showed **No file chosen**, and the owner reported that selecting a PDF opened it in a local viewer. No selected `File` had reached the React form in that observation. The earlier dashed upload box had no drop handler or explicit selection-to-submission instructions. A browser's default dropped-file navigation was therefore not intercepted by that box. This is a verified UI gap; the precise reason the owner's native picker opened a viewer has **not** been independently reproduced on that host.

The real Chromium acceptance test now clicks the input, observes a `filechooser` event, selects a fictional PDF, confirms its filename, then exercises the drop fallback and explicit submission. A functioning standard file chooser is observed in that test. This does not establish that every embedded browser/file-picker bridge behaves identically.

A second, independent configuration blocker was verified through the protected local API: the owner-created Data Science programme had a real `www.xmu.edu.my` programme URL under the fictional demonstration institution, whose official host is `curriculum.example.invalid`. Existing backend origin checks correctly refuse that mismatch. The record was **not changed or removed**. A real university document needs its correctly registered, authorised institution/programme; it must not be silently represented as a fictional university source.

The local application was serving the latest Phase 8 source at the start of this work, with FastAPI and an actual polling worker using the same owned PostgreSQL preview schema. It was not an absent-backend failure in the successful controlled test. The original Replit Run button historically targeted a different, older checkout after the separate Phase 8 preview was stopped. Current Replit state could not be re-inspected because the browser tool repeatedly reported access disabled, including after an owner restoration confirmation. No access restriction was bypassed.

## PDF selection, storage and revision workflow

[The upload page](../frontend/src/pages/Upload.tsx) now accepts one PDF through either the normal picker or an actual drop handler. Dropping prevents default navigation, applies the same type/size validation and displays explicit selected-file status. Invalid or multiple files cannot enable submission. A selected file is not uploaded until **Upload and queue extraction** is chosen. The optional URL is attribution, not a PDF downloader.

The existing nonempty/20,000,000-byte, extension/MIME and `%PDF-` signature checks remain. A pre-submit origin warning mirrors the official-host requirement without changing any URL or relaxing backend validation. API scope, institution ownership, secure private storage and extraction limits remain authoritative on the server. No database model, migration or provider adapter was replaced.

The actual path is protected raw `application/pdf` POST → bounded private storage → persisted `CURRICULUM_PDF_UPLOAD` job → existing worker → extracted course candidates and immutable revision → protected committed-course read. HTTP 202 is only queue acceptance. The UI distinguishes no selection, invalid input, forbidden access, database/API failure, pending work, failed/unsupported layouts, missing or empty revisions and a nonempty revision retrieved for review.

The job contract has no worker heartbeat. After more than a minute without completion, the UI explicitly reports **worker availability unknown** and asks the operator to inspect the worker/database before resubmission. It never infers a stopped worker from queue age.

Supported labelled year-column text PDFs are automatically extracted. General/scanned/ambiguous brochures are not promised automatic extraction. Unsupported-layout failures offer **Reviewed input**. Inspect titles, year/semester/elective flags and exact original locators; submit a complete, explicitly reviewed source-attributed inventory for corrections. That creates a new immutable revision. There is no blanket approval action, no invented syllabus and no claim that extraction certifies taught content. Revision readiness appears only after a successful nonempty committed-course read.

An import older than the current stored source snapshot remains historical; the UI now explicitly says that it did not replace the active curriculum. Do not alter genuine source dates just to activate a record. The browser fixture records its fictional review at the actual later review step. The final test and independent SQL read verify that this later reviewed revision becomes active while preserving the prior PDF revision.

## Controlled judge access and revocation

There is no public unauthenticated guest/session service. The supported fallback is an **authenticated controlled read-only preview**. An administrator privately gives the judge only the launcher's `reader` token, scoped to the isolated fictional institution(s), with exactly `read` permission. Never share the complete `auth.private.json`: it also contains operator/admin test grants. Do not use an institution containing real/private records as the judge scope.

Enter the reader token in the normal **Scoped operator credential** field, then choose **Explore Sample Programme**. No PDF or new model generation is needed. The UI hides upload and review controls; the API independently denies upload, live-analysis, review and global-source operations. A foreign institution grant cannot read the sample. Browser credentials remain in tab memory and are cleared on disconnect/reload; they are not bundled, placed in URLs or stored in local/session storage.

The private access policy stores hashes and is read on each request. Removing the reader principal revokes its subsequent access. Ending the owned preview revokes the entire ephemeral environment and removes its schema only after the worker stops. A copied token-only file must also remain private and be removed when no longer needed. Controlled shared tokens have no named judge identity, automatic expiry or SSO; do not present them as production authentication.

The synthetic launcher clears provider credentials, explicitly installs mocks and blocks provider HTTP. Its process-only execution gate permits the **mocked synthetic workflow**; the `access-context` flag can therefore be true inside this test scope. This is not a persistent external-processing approval or evidence of a paid request. Read-only authorisation independently prevents judge submissions. Persistent external-processing/research defaults stay disabled, and the launcher does not read or modify them. Actual Phase 8.1 paid usage and billing are not observed; live request count is zero.
